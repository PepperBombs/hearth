# Notes: apps made in Hearth, the sandbox, the chat and the assistant's switches

`packages/server/src/made`, `packages/server/catalog`, `packages/server/src/apps/fetch.ts`, `packages/server/src/model`, `packages/server/src/assistant`, `packages/web/src/made`, `packages/web/src/assistant`, `packages/web/src/pages/chat.tsx`, and the manifest rules of `packages/sdk`. The design is `docs/platform.md`; the switches are "The switches" in section F of `docs/mini-app-contract.md`.

Notes for whoever changes this part, people and agents alike. They are read when needed, not at the start of every session: add what you learn as one line, and correct a note in the change that makes it untrue.

- The frame's sandbox needs `allow-forms` (attribute and CSP alike): without it a browser never fires a form's submit event, so every form of a page is dead. `form-action 'none'` is what keeps a form from being sent.
- A frame reports the body's height, with its margins: the document's `scrollHeight` is never less than the iframe's own height, so a frame sized by it only ever grows.
- Newer Chromium returns a promise from `scrollIntoView()`: an effect written as `useEffect(() => el.scrollIntoView())` returns it, and React later calls it as the cleanup and throws. Write effects with a block body.
- Version 1 of `@anthropic-ai/sdk` sends the key as `Authorization: Bearer`, not `x-api-key`; a stand-in that checks the header must look there.
- `made_apps` refers to its install with a deferred foreign key, so that `createMadeApp` writes the app first and lets `addApp` (which asks the registry) find it in the same transaction.
- A dev server without `HEARTH_SECRET` makes one up per process: after a restart every saved key is unreadable and the chat answers `no_key` until it is entered again.
- The chat's history is kept on the server (`chats` and `chat_entries`, migration 8), and all its SQL is in `src/model/chats.ts`, every statement scoped by space and person; the routes are in `src/model/routes.ts`. The browser sends only the new message (up to 20,000 characters, well inside the 64 kB `/api/*` takes); the model gets `historyFor` of the stored entries, the new message included.
- `historyFor` counts its 40,000-character budget text by text, newest first, before joining texts of one side in a row: joined first, two long messages of the person's after a failed turn could leave the newest alone over the budget, and the model would get nothing. So a joined message can be longer than 20,000 characters, and `chatMessageSchema` has no limit.
- `readChat` parses every stored entry with `chatEntrySchema`, and one that no longer reads is answered with 500. Entries are kept for good: add to `CHAT_ACTIONS`, `CHAT_FAILURES` and an entry's fields, and make a new field optional, but never remove or rename one that may be stored.
- The set of conversations answering now (`answering` in `registerModelRoutes`) is in memory: it holds one run per conversation for one server process, which is how Hearth runs. It is let go when the stream ends, and when anything fails before it starts.
- `POST /api/chat` checks, makes a new conversation and keeps the person's message in one immediate transaction (`createChat` and `appendEntry` nest in it), in this order: 404 for the space or the conversation, 409 while it answers, 409 when it holds 500 entries; 409 at 500 conversations for a new one. Only the start of a turn is checked against `MAX_ENTRIES`, so a turn may end past it.
- Each "text", "action" and "error" event is kept (`appendEntry`) before it is sent. When `appendEntry` finds the conversation gone, the run is aborted and the stream ends with no error event, since no failure code fits and nothing may be kept; the page shows its own note. A turn the person stops keeps nothing more, but its message stays, so their next one is joined to it in what the model is given.
- The model never deletes: `delete_rows` keeps a request (`chat_confirmations`, `src/model/confirmations.ts`) and only the person's answer (`POST .../chats/:chatId/confirmations/:id`) deletes, after checking everything again, through `store.ts`. Where a request stands is not kept with its entry: `readChat` merges it from that table every time, so a kept `delete_requested` entry says "pending" for ever and its answer is read beside it. The card keeps the answer in the page's own entries for the rest of the visit, and on a 409 reads the conversation again, since the request may have been answered on another device.
- `historyFor` puts a note of each answered request (`answerNote`, "[Hearth: the person confirmed ...]") on the person's side, before the first message of theirs written after the answer, so it is joined to that message with a blank line, as texts of one side in a row are. A model, the end-to-end stand-in included, gets the note and the message as one text.
- `titleOf` cuts at 80 code points, never inside a character, and adds an ellipsis: a title is up to 81 characters.
- The chat page (`packages/web/src/pages/chat.tsx`) keeps the space and the open conversation in the address (`/chat?space=&chat=`), and adopts a conversation's entries in an effect, not during render: react-router changes the address in a transition, and a reset during render wiped a new conversation's entries the moment its ID arrived. Leaving a conversation while it answers stops its turn, as leaving the page does.
- When a new conversation's ID arrives, the page re-keys its entries and changes the address in one `startTransition`: re-keyed alone, the entries left the screen for one render. A turn of a new conversation that never got its ID (stopped, or left with New conversation, which stops it) leaves nothing for the next message: the server kept it as a conversation of its own.
- Entries read when a conversation is opened are drawn outside the `aria-live` region (`Shown.heard`), so a screen reader announces only what this visit adds. A notice (gone, busy, full, too many) belongs to the conversation it was raised in and goes when the person leaves it. A kept change offers Undo only while the app is still at the version it made (`Undo`'s `made`).
- The page tells the server's three 409s apart by what it sent and the message: no `chatId` means too many conversations, a message with "full" a full one, anything else busy. Change the server's wording with `chat.tsx` in mind, or give each its own code in the contract.
- The list is beside the conversation when the main column is 768px or wider (`@min-[768px]/main`), as the dashboard's grid measures that column: the theme keeps one breakpoint, `md`, so `lg:` classes are never generated and must not be used. Below it, two icon buttons in the top bar open the list in a Dialog ("Conversations") and start a new one, and the top bar names the open conversation: CSS cannot choose a heading's text, so `useNarrow` measures the same 768px in script (`LIST_BESIDE`); change the two together.
- The page fills the room under the top bar (`Page`'s `fill`): the conversation scrolls in its own element and the box to write in stays under it. Opening a conversation and each new entry scroll to the end (a turn ending adds nothing, so it does not); what grows later (an app's frame) keeps the end in view only while the person has not scrolled up (`atEnd`). Since `main` no longer scrolls, the skip link's target cannot be scrolled from the keyboard: the conversation is a focusable region ("Messages") that can. The box is measured again when its width changes, in a `requestAnimationFrame` (resizing it inside its own `ResizeObserver` loops).
- The live region of the conversation stays in the tree when it is empty (`empty:-mt-5`, never `empty:hidden`): a live region that appears together with its content is not announced.
- A model's reply is drawn from Markdown (`packages/web/src/components/markdown.tsx`, react-markdown with remark-gfm); the person's own words never are. HTML in a reply shows as text (never add rehype-raw), links work only to absolute http(s) and mailto addresses (`safeHref`) and open in a new tab with `noopener noreferrer`, and an image is never an `<img>` but a link to it, so a reply makes the browser fetch nothing. Its headings start at h3. A reply the parser throws on (Markdown nested a couple of thousand levels deep overflows its stack) is shown as plain text by an error boundary (`PlainOnError`): there is no other boundary in the app, so without it one reply would blank the whole page, each time its conversation is opened.
- A change to a made app is checked against every stored row (`rowsNotFitting` in `store.ts`), going back to a version too: a strict schema refuses a row with a field the app no longer has, so removing a field that holds data is refused rather than hiding the data.
- A built-in app's rows must fit its manifest exactly, as the old app of the same name stored them (`packages/server/catalog/*/manifest.json`): change a field there and the move of the old apps' installs refuses every one that holds such a row.
- The move of the old apps (`moveLegacyInstalls` in `src/made/builtin.ts`) runs at every start, since a server may still hold installs keyed `grocery`, `ideas` or `trending` of the mini-apps framework that was removed. Each install moves alone, in one transaction, and its rows in `app_jobs` go with the move (`forgetJobs`, the only SQL for that table now). One that does not fit stays as it was, hidden, since the server holds no app of that ID, with its data; the log names it at every start until it moves. Keep the move working, and keep the three IDs as built-in apps.
- A made field that is `required` only has to be there: an empty text passes. A page that needs text checks it itself.
- `hearth.fetch` is `fetchFor` in `packages/server/src/apps/fetch.ts`, in three parts. The rules, at every request: GET to https on the default port, no user name or password, a host the manifest lists exactly; `user-agent: Hearth` and only accept, accept-language, if-modified-since, if-none-match and `x-` names other than x-forwarded-* and x-real-ip; up to 3 redirects, on https to the same host; 20 seconds for each answer, its body included; 2 MiB of body, counted after decompression. Then the pace (`createPace`): requests to one host start 6.5 seconds apart across the whole server, every app and space together, the request a redirect leads to as well. Then a transport, one request and one answer with nothing followed: Node's fetch (`nodeTransport`, `redirect: "manual"`), or the stand-in file. A transport, or a body, that ignores its signal is not waited for, and the route gives a fetch 60 seconds at most, its turn in the pace included.
- Because of the pace, a page that fetches several times waits for each in turn, and shows its progress.
- Only a built-in app names hosts in `network`: `createMadeApp` refuses a manifest with hosts that comes from no template, and a change keeps a built-in copy's hosts as they are, since a host a page names is one the server fetches from, with its own address.
- `serve()` of `@hono/node-server` replaces the globals `Request` and `Response` with lighter classes of its own, and an answer of Node's fetch is no instance of those. `fetch.ts` once asked the global what a `Response` is, so on a server that listened every fetch through Node's transport failed with "the transport gave no answer", whatever the host answered; no test saw it, since made-up transports answer with `new Response` of the global of that moment and every end-to-end server answers from the stand-in file. `fetch.ts` knows an answer by `PlatformResponse`, the class kept when the module loads, never by the global: keep it so, and keep `fetch.ts` loaded before anything listens. Do not switch the replacement off instead (`overrideGlobalObjects: false`): Hono's `bodyLimit` makes a `new Request` of the listener's own request, which only the listener's class can read, and every request with a body it has to count then ends in 500. `src/serve.test.ts` holds the fix where it matters, reading a real answer of Node's fetch from a listener on this machine while `startServer` listens, and `fetch.test.ts` with the global replaced. A test of Node's transport that stands for a real server needs an answer of the real `fetch`, not `new Response`.
- The tests of `fetch.ts` give a made-up transport, or a made-up `fetch` that returns real `Response` objects, and a `Clock` that moves only when told (`fakeClock`, `src/apps/test-clock.ts`): keep the rules tested that way, never against a real host, and nothing in them waiting for real time.
- `HEARTH_FETCH_STANDINS` names a JSON file whose stand-ins answer every fetch of every app (`standInFile`), at once and unpaced, read again at every request, so a test changes the answers by writing it: write it whole, as a new file renamed into place. `loadConfig` refuses the setting unless `HEARTH_AUTH=dev`, which needs a loopback `HOST`, so a real server cannot have it, and the server says at start-up when it is on. The rules still come first, so a stand-in opens no host the manifest does not list. A request no entry answers, and every request while the file is missing or not a list of stand-ins, fails as `network` with a message that says so. The format is in `packages/server/README.md`.
- In `pnpm dev` a built-in GitHub Trending fetches from the real `api.github.com` when someone who may edit it opens it, from this machine's address, which GitHub allows 10 searches a minute without a token. To work on it without reaching GitHub, start `pnpm dev` with `HEARTH_FETCH_STANDINS` naming a file by an absolute path (the server's working directory is `packages/server`). Nothing automated may reach GitHub.
- A page can be tried without a server: render it with `frameDocument` in an iframe whose parent answers the bridge from memory, checking rows with `collectionSchemas`. The built-in pages were checked that way.
- `frame.tsx` tells an app's other frames to read again after a write alone (`WRITES`): after a read too, two frames of one app on screen (a card and the chat's) would wake each other for ever.
- A rule across rows that a page keeps (one grocery item per name) holds only against what the page last read: the server checks each row by itself, and two people in the same second can both add.
- `MadeAppFrame` keys its iframe by space and app: React keeps a component when only the route's IDs change, and a reused iframe would answer the page shown before, still loading or still sending, as the next app.
- The settings dialog starts its form from the first answer it gets. A made app's pages read settings through the bridge, not the query cache, so a cached answer may be old: `AppSettingsButton` drops the cached one before opening.
- The bridge's height report skips the echo of a page sized to its frame (`min-height: 100vh` with padding): the frame grew and the page still overflows it by as much as before. Models write such pages often.
- A made app's settings are checked by the SDK's own rules: the server works out an SDK manifest from the made one (`asSdkManifest`) and checks it with `manifestSchema` (`checkMadeManifest`). The SDK describes a manifest twice, and the two must agree: the types in `packages/sdk/src/index.ts` and the schema in `manifest-schema.ts`. Change both. The schema holds what the types cannot: `network` is 1 to 10 lower-case DNS names of two or more labels, the last letters only (so no scheme, port, path, wildcard or IP address), none twice and none of the local network (`localhost`, `*.localhost`, `*.local`, `*.internal`, `home.arpa` and below); it counts the hosts itself, because zod's `.max()` on a list also measures a text given in its place. `@hearth/sdk` itself imports nothing; zod stays in `manifest-schema.ts`.
- The SDK's type tests (`expectTypeOf`, `@ts-expect-error` in `packages/sdk/src/index.test.ts` and `manifest-schema.test.ts`) fail in `pnpm typecheck`, not in the test runner.
- The assistant is each person's own model, in the chat. Every tool of it reaches an app with `by: "assistant"` (`MadeRequest`, `madeAppsIn`), so what it may do is `VISIBLE`'s `assistant`, read inside the tool's transaction: the person's access capped by the space's level (`spaces.assistant`: Off, where every space starts, Read only or Read and change), and nothing in an app its owners left out (`space_apps.assistant`). Work it out no other way (`docs/notes/server.md`).
- `create_app` asks the space's own level, since a new app has no install to look up: it needs Read and change (`assistantMayChange`), so that the chat makes apps only where it may also fill them. A space that is Off answers every chat `assistant_off`; its owners can switch it to Read and change there ("Allow it here"), or choose any level and the apps on the Assistant card in Settings.
- The switches were built for the connector for Claude (section F), which the owner removed in November 2026 with its endpoint at `/mcp`, its tools, the card's address and its end-to-end project. What is left is the level's route (`PUT /api/spaces/:spaceId/assistant`, `src/assistant`), `assistant` in the access route, `VISIBLE`'s rule and the card; `src/assistant/switches.test.ts` holds the first three, and `e2e/assistant-card.spec.ts` the card on a phone.
- The web app loads the session once. The Assistant card reads it again when it comes on screen and when the window is looked at again (`useSessionReadAgain`, not within 5 seconds of the last reading), since a space's level may have been changed by another owner, from the chat or on another device, and a card that shows an old level turns an owner's next press into its opposite. Because the session is now read while a page is open, `adopt` in `session/preferences.tsx` lets the note of an unsaved theme or language win also while its save is on its way, and a save that went through reads the session anew: an answer from before the save must not put the old choice back. Do not reload the session after a save that failed: `adopt` sends an unsaved choice again whenever a session arrives, and the two would go round.
